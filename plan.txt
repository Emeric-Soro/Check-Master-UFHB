# Plan d’implémentation — Évaluations M2/S3, import Excel et nouveaux modèles

## Résumé

Mettre en place un référentiel unique pour le semestre actuellement nommé S3, S9 ou M2 S1. Le nom interne sera `M2_S1`, avec les trois appellations comme alias.

Le système permettra de :

- gérer les UE, leurs crédits et leurs versions historiques ;
- saisir les notes par étudiant et par UE ;
- distinguer session normale et rattrapage ;
- calculer automatiquement les totaux pondérés ;
- déterminer automatiquement le statut Nouveau/Redoublant ;
- importer les évaluations Excel avec prévisualisation et validation ;
- produire le nouveau PV d’épreuves écrites ;
- intégrer les modèles d’autorisation de soutenance et de suivi d’encadrement ;
- afficher sur le tableau de bord les membres ayant réellement donné leurs observations.

## 1. Modèle de données

### Référentiel des semestres

Conserver une seule occurrence physique du semestre M2/S1 et ajouter une table d’alias :

- semestre canonique : `M2_S1` ;
- alias acceptés : `S3`, `S9`, `M2 S1`.

Les recherches, imports et éditions utiliseront toujours l’identifiant canonique. Les libellés affichés resteront configurables selon le document produit.

### Table `ue`

Créer une table référentielle contenant au minimum :

- `id_ue` ;
- `code_ue` ;
- `libelle_ue` ;
- `credit_ue` ;
- `date_credit` ;
- semestre canonique ;
- niveau/parcours ;
- numéro de version ;
- dates d’effet ;
- état actif/inactif.

Une modification de libellé ou de crédit créera une nouvelle version. Une ancienne version ne sera jamais modifiée si elle a déjà été utilisée dans une évaluation. Chaque évaluation pointera vers la version exacte de l’UE applicable à sa période.

Les codes officiels seront saisis par la scolarité avant tout import. Un code absent ou inconnu bloquera l’import concerné.

### Table `evaluation_s3`

Créer une table dédiée aux notes du semestre M2/S1 :

- `id_evaluation` ;
- identifiant étudiant ;
- `id_ue` ;
- année académique ;
- `note_obtenue_ue` sur 20 ;
- `date_note` ;
- `session_normale` : booléen ;
- utilisateur de création/modification ;
- source et lot d’import éventuel ;
- horodatage.

Ajouter une contrainte d’unicité sur étudiant, UE, année académique et session afin d’éviter les doublons.

Le total d’une UE sera calculé ainsi :

`note / 20 × credit_ue`

Les totaux ne seront pas saisis manuellement. Les crédits attendus seront calculés à partir du référentiel actif ; le système signalera toute maquette dont le total n’est pas égal à 30 crédits.

La moyenne d’une session sera calculée par :

`Σ(note × crédit) / Σ(crédits)`

Les notes normales et de rattrapage seront conservées séparément. Par défaut, le PV utilisera la session demandée, normale par défaut, sans remplacer automatiquement une note normale par une note de rattrapage.

### Statut étudiant

Ajouter `nouveau` dans `etudiants` comme projection du statut M2 courant, affichée sous la forme `Nouveau` ou `Redoublant`.

Pour conserver l’historique, ajouter également `nouveau_m2` dans la table de statut annuel existante ou dans une table dédiée par étudiant et année académique. Cette valeur sera la source métier ; `etudiants.nouveau` sera recalculé lors du changement d’année active.

Règle automatique :

- première inscription ou première trace M2 : `NOUVEAU = OUI` ;
- inscription, évaluation ou historique M2 antérieur : `NOUVEAU = NON` ;
- aucune saisie manuelle ne remplacera cette règle sans mécanisme d’audit.

Les historiques incomplets devront être signalés à l’administrateur pour vérification.

## 2. Services, interfaces et import Excel

### Interface de saisie

Créer une interface dédiée aux évaluations M2/S1, en remplacement ou extension de la saisie actuelle des moyennes globales :

- sélection de l’année académique ;
- recherche de l’étudiant ;
- affichage de son statut Nouveau/Redoublant ;
- grille des UE officielles ;
- note normale, crédit, total ;
- note de rattrapage, crédit, total ;
- date d’évaluation ;
- totaux et moyenne par session ;
- contrôle du total de crédits ;
- sauvegarde transactionnelle de toutes les lignes.

Une cellule vide signifie « non évalué » ; la note `0` reste une note valide. Les anciennes années pourront être verrouillées selon les permissions.

Créer un service central de calcul des résultats afin que l’interface, les relevés, les bulletins et les PV utilisent exactement les mêmes règles.

Les anciennes moyennes M1/M2 de la table `notes` seront conservées pour compatibilité pendant la migration, mais les nouveaux résultats détaillés deviendront la source principale du M2/S1.

### Import Excel

Utiliser PhpSpreadsheet, déjà présent dans le projet.

Le modèle d’import officiel contiendra les colonnes :

- `annee_academique` ;
- `semestre` ;
- `identifiant_etudiant` ;
- `code_ue` ;
- `note` ;
- `date_evaluation` ;
- `session_normale`.

Le traitement sera en quatre étapes :

1. dépôt et analyse du fichier ;
2. normalisation des dates, nombres décimaux et libellés de session ;
3. résolution des étudiants, alias de semestre et codes UE ;
4. prévisualisation avec erreurs, avertissements et doublons.

La confirmation créera un lot d’import auditable et exécutera une transaction atomique. Aucun lot confirmé ne devra produire une importation partielle silencieuse.

Contrôles obligatoires :

- extension et taille du fichier ;
- en-têtes attendus ;
- note comprise entre 0 et 20 ;
- étudiant existant ;
- année académique valide ;
- code UE officiel ;
- semestre M2/S1 ;
- date correcte ;
- doublons dans le fichier ou déjà présents en base ;
- cohérence entre l’UE et la version applicable.

Le même lot pourra être rejoué sans créer de doublon. Les lignes rejetées resteront consultables avec leur motif.

Le classeur de maquette servira uniquement à initialiser les UE et les crédits. Comme ses codes UE sont vides, il devra passer par une étape de correspondance avec les codes officiels avant utilisation.

## 3. Nouveaux documents et modèles

### PV d’épreuves écrites

Créer un générateur dédié reproduisant le modèle fourni :

- en-tête institutionnel ;
- identité de l’étudiant ;
- statut et identifiants ;
- année de validation du S3/M2 S1 ;
- tableau de 8 colonnes ;
- codes et libellés UE ;
- session normale : note, crédits, total ;
- session de rattrapage : note, crédits, total ;
- total de 30 crédits ;
- moyenne sur 20 ;
- partie soutenance du mémoire ;
- résultat final ;
- composition et signatures du jury.

Le modèle sera enregistré dans le registre documentaire avec un code dédié, par exemple `PV_EPREUVES_ECRITES`. Il devra être prévisualisable, générable, téléchargé et historisé comme les autres documents.

### Autorisation de soutenance

Créer un modèle reprenant la première page du PDF fourni :

- identité ;
- niveau, année académique et option MIAGE/GI ;
- contacts ;
- entreprise d’accueil ;
- période de stage ;
- thème ;
- maître de stage ;
- encadreur pédagogique ;
- directeur de mémoire ;
- session demandée ;
- avis et signatures.

### Fiches de suivi d’encadrement

Créer deux variantes :

- suivi par le directeur de mémoire ;
- suivi par l’encadreur pédagogique.

Chaque fiche contiendra les informations de l’étudiant, du stage et un tableau de rendez-vous avec date et signatures. Ajouter une table de suivi des rendez-vous si aucune structure existante ne couvre ces informations.

Le terme fonctionnel `Superviseur` sera harmonisé avec le rôle existant `Encadreur`. Aucun doublon de modèle ne sera créé.

### Compte rendu de commission

Remplacer les libellés de type « template » par « modèle » et rendre le modèle configurable :

- ordre du jour avec décision « suivant » ou « adopté » ;
- nombre variable de membres ;
- ajout et retrait des membres ;
- commentaire facultatif ;
- affichage automatique de `RAS` lorsqu’aucune observation n’est fournie ;
- mention claire de l’administrateur ;
- mise en page conforme aux PV demandés par la scolarité.

## 4. Tableau de bord de commission

Ajouter un lien sur chaque membre de la commission vers une vue d’observations détaillée.

Cette vue devra distinguer :

- membre ayant reçu le dossier ;
- membre ayant validé ou donné une observation ;
- membre n’ayant encore rien renseigné ;
- commentaire ;
- décision ;
- date de saisie ;
- rapports concernés.

Le lien devra filtrer automatiquement la commission et le membre sélectionnés. Les données seront en lecture seule et protégées par les permissions de commission.

Le calcul utilisera les tables d’évaluation et de validation existantes, sans confondre la réception d’un dossier avec la fourniture d’une observation.

## 5. Migration, sécurité et compatibilité

Avant développement, vérifier le schéma réel de la base, car les exports SQL et certaines requêtes actuelles présentent des écarts.

La migration devra :

- créer les nouvelles tables, clés étrangères et index ;
- être rejouable sans erreur ;
- initialiser les alias du semestre M2/S1 ;
- préserver la table `notes` et les anciennes évaluations ;
- ne jamais inventer de notes par UE à partir d’une moyenne globale ;
- journaliser les imports et modifications ;
- appliquer les contrôles CSRF, permissions et audit déjà utilisés par l’application.

Une phase de comparaison permettra de vérifier les résultats détaillés avec les anciennes moyennes avant de rendre le nouveau calcul officiel.

## 6. Tests et critères d’acceptation

Prévoir des tests automatisés et visuels pour :

- création et versionnement des UE ;
- correspondance S3/S9/M2 S1 ;
- calcul note/crédit et moyenne pondérée ;
- distinction normale/rattrapage ;
- note zéro et UE non évaluée ;
- contrôle des 30 crédits ;
- détermination Nouveau/Redoublant ;
- doublons et rejouabilité des imports ;
- dates et décimales Excel ;
- étudiants ou codes UE inconnus ;
- rollback complet d’un import invalide ;
- contrôle des droits et de la lecture seule ;
- saisie et recalcul de la grille ;
- génération du PV avec les 9 UE MIAGE et les deux sessions ;
- rendu visuel du PV, de l’autorisation et des fiches de suivi ;
- affichage correct des observations et de `RAS` ;
- protection des données de commission.

Les documents PDF devront être rendus en images pour vérifier la mise en page, les sauts de page, les signatures, les colonnes et la lisibilité.

## Hypothèses retenues

- `M2_S1` est le nom interne unique ; S3, S9 et M2 S1 sont des alias.
- Les codes UE sont fournis et validés par la scolarité avant import.
- L’import Excel suit le cycle prévisualisation, correction puis confirmation.
- Le statut Nouveau/Redoublant est calculé automatiquement à partir de l’historique.
- Les versions d’UE sont immuables après utilisation.
- Les anciennes tables et fonctionnalités restent compatibles pendant la transition.
- Les modifications existantes dans le dépôt doivent être conservées et intégrées sans écrasement.
