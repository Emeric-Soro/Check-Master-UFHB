2. CHANTIER A — MIGRATION DES DOCUMENTS VERS PHPOFFICE/PHPWORD
================================================================================

2.1 OBJECTIF ET PÉRIMÈTRE
-------------------------
Remplacer, pour la MAJORITÉ des documents générés, la chaîne actuelle
« HTML → TCPDF » par « modèle .docx UFRMI → PHPWord TemplateProcessor →
DOCX et/ou PDF en PHP pur ». Bénéfices attendus : documents éditables
(DOCX) conformes aux modèles Word de l'UFRMI, maintenance simplifiée des
gabarits, rendu PDF délégué à mPDF/Dompdf (moteurs modernes, meilleur CSS).

RESTENT HORS PÉRIMÈTRE PHPWord : les documents importés (rapports étudiants
uploadés), les exports de données (CSV/XLSX, PhpSpreadsheet déjà en place),
les vues imprimables navigateur (window.print).

2.2 ÉTAT DES LIEUX — POINT DE DÉPART
------------------------------------
- PHPWord 1.4.0, mPDF 8.3.1, Dompdf 3.1.5 : installés, jamais utilisés → zéro
  régression à craindre, mais zéro retour d'expérience : le prototype (2.9) est
  obligatoire.
- Aucun modèle .docx officiel UFRMI n'existe encore dans le projet : les
  modèles devront être créés (à partir des documents Word actuels de l'UFRMI)
  puis déposés dans un répertoire sécurisé.
- TCPDF reste le moteur de référence des documents non migrés (fallback).

2.3 STRATÉGIE GÉNÉRALE : MODÈLES .DOCX + TEMPLATEPROCESSOR
----------------------------------------------------------
- Chaque type de document = un modèle .docx officiel (Word de l'UFRMI),
  balisé avec ${ma_variable} : ${nom_etudiant}, ${matricule}, ${mention},
  ${note_jury}, ${ue_code}, ${session}, ${annee_academique}, etc.
- Traitement : new \PhpOffice\PhpWord\TemplateProcessor('/chemin/modele.docx')
  puis setValue('nom_etudiant', ...) ; répétitions de lignes : cloneRow('ue_code',
  count($ues)) ; blocs conditionnels : cloneBlock('bloc_mention', n).
- Échappement systématique des valeurs (guillemets, accents, caractères
  spéciaux), gestion des valeurs nulles (ne jamais injecter « null »).
- Identité du modèle : version + date en métadonnées DOCX (core properties).

2.4 RÉPERTOIRE DES MODÈLES (SÉCURISÉ)
-------------------------------------
- Emplacement proposé : storage/templates/ (hors public/, non servi par
  Apache ; à confirmer par le test HTTP) OU app/templates/.
- Contrôles : vérifier qu'une requête HTTP directe renvoie 403/404 ;
  bloquer explicitement dans le .htaccess racine si besoin (voir 4.3).
- Nomenclature versionnée : {code_type}_{version}.docx
  (ex. releve_notes_v01.docx, bulletin_v01.docx).
- Les modèles sont des BIENS UFRMI : stockés en base (BLOB) ou en disque avec
  sauvegarde, jamais modifiés par l'application.

------------------------------------------------------------

2.6 ARCHITECTURE CIBLE (9 ÉTAPES PAR DOCUMENT)
----------------------------------------------
 1. Contrôleur existant (inchangé côté appels) → session + permission
 2. Service métier : collecte de DONNÉES TYPÉES (au lieu des $GLOBALS actuels
    de releve_notes.php) ; extraction progressive des DataUtils existants
    (PlanningDataUtils, RecuDataUtils)
 3. Chargement du modèle autorisé (registre de modèles, anti-traversal,
    pas de nom de fichier fourni par l'utilisateur)
 4. TemplateProcessor : setValue/cloneRow/cloneBlock selon les données
 5. Génération du DOCX temporaire dans un dossier NON public (storage/tmp/)
 6. Contrôles avant rendu : existence, taille, signature ZIP valide, MIME
 7. Rendu PDF en PHP pur : mPDF ou Dompdf (via PHPWord Settings ou conversion
    DOCX→HTML intermédiaire), choix par type de document (voir 2.7)
 8. Stockage via DocumentStorageService existant (référence, version, MIME,
    entité, utilisateur, statut actif/archive, journal) — table documents
 9. Purge du temporaire (try/finally, pas de fichier orphelin)

2.7 RENDU PDF SANS LIBREOFFICE (OPTIONS PAR TYPE)
-------------------------------------------------
Option 1 — Convertisseur interne PHPWord (driver mPDF ou Dompdf) :
  \PhpOffice\PhpWord\Settings::setPdfRendererName(
    \PhpOffice\PhpWord\Settings::PDF_RENDERER_MPDF);
  \PhpOffice\PhpWord\Settings::setPdfRendererPath('/chemin/vendor/mpdf/mpdf');
  IOFactory::createWriter($obj, 'PDF')->save($chemin);
  → à valider au prototype : fidélité des tableaux/accents sur les modèles
    UFRMI (mPDF reconnu plus fidèle que Dompdf pour les tableaux Word).
Option 2 — Template HTML/CSS intermédiaire → mPDF ou Dompdf :
  pour les documents G2 (contenu libre) : réutiliser les gabarits HTML
  existants (releve_notes.php, etc.) et remplacer uniquement TCPDF par
  mPDF/Dompdf. Gain immédiat, risque faible.
Option 3 — Conservation TCPDF : pour G3 (reçu, PV final) et en fallback
  général si un rendu ne passe pas la validation.

DÉCISION REQUISE (voir §7) : DOCX seul, PDF seul, ou les deux par type ?
Recommandation : produire les DEUX (DOCX éditable + PDF de diffusion), le
DOCX étant la sortie native de PHPWord.

2.9 TESTS DE VALIDATION (avant migration de chaque type)
--------------------------------------------------------
 1. Rendu conforme au modèle Word UFRMI (comparaison visuelle PDF)
 2. Polices/accents français corrects (é, è, ê, ç, œ)
 3. Tableaux multi-pages corrects (cloneRow)
 4. Logos et en-têtes institutionnels présents (resolveLogoPaths)

 8. PDF généré en < 30 s, taille raisonnable, pas d'erreur mémoire
 9. Droits : seul le public autorisé accède au document (canView)
10. Pas d'accès direct aux modèles via HTTP
11. Versionnage : régénération = nouvelle version, ancienne conservée
    (statut actif/archive)

3. CHANTIER B — RÉÉCRITURE, CHIFFREMENT ET MASQUAGE DES URLS
================================================================================

3.1 OBJECTIFS
-------------
- Éliminer les extensions .php visibles dans les URLs.
- Remplacer les identifiants bruts (id=1402, num_etu=CI0115004687, etc.)
  par des jetons opaques non prédictibles.
- Centraliser la création d'URLs (une seule fonction/helper) pour ne jamais
  régénérer d'URLs exposées par erreur.
- Conserver la compatibilité (redirections) le temps de la migration.

3.2 ÉTAT DES LIEUX — LES DEUX SYSTÈMES
--------------------------------------
- LÉGACY (majorité) : layout.php?page=X&action=Y&id=Z — 50 fichiers routes,
  151 vues. C'est lui qui expose le plus de paramètres.
- NOUVEAU (partiel) : index.php?_path=/login — routeur app/Core/Router.php.
- Point d'ancrage recommandé : router unique, mappage
  page/action legacy → route propre, puis réécriture Apache.

FORMES D'URLS CIBLES (exemples) :
  /connexion                              (au lieu de layout.php?page=connexion)
  /app/tableau-de-bord                    (au lieu de index.php?_path=/dashboard)
  /documents/rapport/{jeton-opaque}                 (consultation)
  /documents/rapport/{jeton-opaque}/telecharger     (téléchargement)
  /documents/pv-final/{jeton-opaque}
  /reinitialisation-mot-de-passe/{jeton}  (au lieu de reset_password.php?token=...)

3.3 STRATÉGIE DE RÉÉCRITURE APACHE (.htaccess RACINE À CRÉER)
-------------------------------------------------------------
- RewriteEngine On ; RewriteBase /
- Front controller unique : toutes les requêtes non-fichier/non-répertoire →
  index.php (ou router), SAUF exclusions : /assets/, /uploads/, /logs/,
  /vendor/, /storage/ (interdit), fichiers réels existants (RewriteCond
  %{REQUEST_FILENAME} -f / -d).
- Règles explicites pour les routes documents :
  ^documents/rapport/([A-Za-z0-9_-]+)$            → ?page=visionneuse_document&type=rapport&token=$1 [L,QSA]
  ^documents/rapport/([A-Za-z0-9_-]+)/telecharger → ?page=visionneuse_document&type=rapport&token=$1&action=download [L,QSA]
  (idem pv-final, bulletin, releve-notes, planning, etc. — un seul pattern
  par famille)
- Redirections anciennes : 301 des anciennes URLs documentées (matrice §3.6)
  vers les nouvelles, avec date de retrait programmée.
- Anti-pièges : éviter les boucles de réécriture (vérifier %{ENV:REDIRECT_}),
  éviter le double décodage (%2F, %252F), 403/404 cohérents (page d'erreur
  unique, sans énumération), tester les slashs finaux et les méthodes HTTP.
- Valider avec l'onglet « Réécriture .htaccess » de server_audit.php AVANT
  suppression de l'audit.

3.4 JETONS OPAQUES — CHIFFREMENT DES IDENTIFIANTS
--------------------------------------------------
REGLES DE BASE (issues de l'audit et des bonnes pratiques) :
- NE JAMAIS utiliser AES-ECB (mode dangereux, pattern répétitif visible).
- Ne pas « chiffrer » pour masquer : un jeton doit être IMPRÉVISIBLE.
- Masquage ≠ autorisation : le contrôle d'accès (canView, permissions)
  reste appliqué côté serveur APRÈS décryptage.

DEUX APPROCHES COMPLÉMENTAIRES (à choisir en §7) :
Approche 1 — JETON ALÉATOIRE (recommandée pour la plupart des cas) :
  identifiant non séquentiel généré (random_bytes(16→24) → base64url sans
  padding) stocké en base (table documents.jeton_public, unique index) ;
  lien jeton → type/entité/version/expiration ; lookup par index unique.
  Avantages : zéro dépendance à une clé, révocable individuellement.
Approche 2 — JETON CHIFFRÉ (si confidentialité du contenu nécessaire) :
  AES-256-GCM (openssl_encrypt avec nonce + tag), clé secrète stockée HORS
  du code public (fichier hors webroot ou variable d'environnement LWS),
  sortie base64url sans padding, nonce transmis avec le tag dans la charge
  utile ; expiration : timestamp dans la charge utile (ex. validité 1 h pour
  un lien de téléchargement ponctuel, 24 h pour un lien d'accès) ;
  vérification : hash_equals pour comparer les jetons, refuser tout jeton
  vide/court/malformé/expiré/altéré (échec → 403/404 personnalisé sans
  révéler la cause).
- Lier TOUJOURS le jeton au type de document (jamais de jeton « universel »)
  et à la version ciblée.

3.5 DONNÉES À NE JAMAIS METTRE DANS UNE URL
-------------------------------------------
- id_rapport, id_document, id_CR, id_inscription (IDs internes)
- num_etu / matricule (données personnelles)
- chemins physiques de fichiers
- clés de chiffrement ou secrets
- base64 ≠ chiffrement : ne pas confondre encodage et protection
- paramètres de recherche/filtres (p, search, niveau) : autorisés en
  querystring APRÈS le jeton pour les listes internes, jamais pour l'accès
  à un document.

------------------------------------------------
Champs de la matrice (un tableau par fichier plan_matrices_urls.txt) :
  ancienne URL | cible propre | méthode | contrôleur/route | paramètres
  requis | permission | comportement non connecté | codes HTTP | compat
  anciens liens | date de retrait

PRIORITÉ 1 — DOCUMENTS (le plus exposé) :

  ?page=visionneuse_document&type=rapport&id=42
